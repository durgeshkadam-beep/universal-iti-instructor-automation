# MCQ action context and retry behaviour

Instructor publication and Student start/resume/submission controls belong to the user, role, workspace and render that created them. Workspace loading invalidates earlier controls even when loading the same workspace again. Changing account/role/workspace, replacing the exam view or detaching its form/card prevents an old handler from sending a new action. Read-only roles and loading sessions clear old examination controls instead of leaving a previous user's form visible.

A request already sent may still complete in its original workspace. Late responses cannot populate a new card or claim publication in the newly selected context. Reopen the original workspace/test to check authoritative status before retrying. This supplements the existing token-await API context checks; backend membership, private answer keys, timing and transactional grading remain authoritative and unchanged.

Duplicate in-flight start/submission handlers are ignored. Publication fields are locked while the reviewed payload is being sent. Student answer inputs are locked during submission so the visible selection cannot drift from its submitted payload. A failed request in the same active context restores editing with the selected answers/authoring text intact. A completed result remains locked and is shown once. The advanced JSON publisher has the same context check and locks its input while sending.

Selections are retained only in the current open test form. Reloading/navigating does not restore a private answer draft; persistent Instructor question drafts, offline examinations and retakes remain unimplemented. There is no new local answer-key/score storage or AI/provider requirement. A timeout is not proof that the server rejected an already-sent request; resume/reload to check the immutable result.

Validation reproduces the old wrong-workspace requests before the fix. Executable DOM cases cover stale forms/cards, load invalidation, role/account changes, late sessions/publications, duplicate handlers and retry input retention. Desktop/mobile tests use real Auth/Firestore/HTTP, verify zero requests and no result for stale controls, then publish and grade a current synthetic exam normally. Final complete results/source and actual staging acceptance are recorded in Draft PR #16. No backend/rules change or production deployment is needed.
